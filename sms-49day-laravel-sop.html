1. Executive Summary & Feasibility Verdict

Verdict: the system as listed in the brief cannot be built in 49 days by 6 interns. A deliberately reduced MVP can. The brief lists roughly 11 module families and 90+ features. Honest measurement of intern capacity gives about 470 effective engineering hours for feature work. The full brief is a 1,400–1,900 hour build. The plan below therefore delivers a defensible core — an institution can admit students, structure academics, enroll, take attendance, examine, grade, publish results, bill, collect fees, and report on all of it — and explicitly excludes Library, multi-campus, payroll, transport, hostel, online payment gateways, public API, and LMS.

What the client gets on Day 47

  • A deployed Laravel 11 application on one Linux server with HTTPS, queue worker, scheduler, nightly backups.
  • Six roles with a database-backed permission system and policy-enforced authorization on every resource.
  • Student lifecycle: admission → profile → guardians → documents → enrollment → attendance → exam marks → grades → published results → printable report card.
  • Finance: fee structures → invoices per term → payments → receipts → outstanding balance reports.
  • 11 operational reports with CSV export, 3 PDF documents, announcements + email/in-app notifications, full audit trail.
  • ~180 automated tests, a manual regression pack, and the complete handover package in §29.

Rule 1 applied — complexity not hidden. 3.3 Risk analysis by category

Scope risks

  • Brief contains ~90 features; MVP must reject ~45 of them. Without written sign-off on §4, scope creep is near-certain.
  • "Reports" is unbounded — capped at 11 named reports.
  • Library looks small but is a full domain (5 tables, fines, availability logic).

Technical risks

  • Grading/GPA engine is the only genuinely complex algorithm; owned by the strongest developer (D1), built with unit tests first.
  • Timetable clash detection is a classic intern trap — MVP limits it to teacher/room/section clash within one term, no auto-generation.
  • Money handling in floats. Mandated: integer minor units (bigInteger cents) or decimal(12,2) + bcmath. Never float.

Schedule risks

  • Week 1 produces almost no features (ramp + design). Accepted and planned.
  • Exams/results (Week 5) depend on Weeks 2–4 being clean; a slip there cascades. Buffer day = Day 33.
  • Client unavailability for UAT on Day 43–44 — book it on Day 1.

Intern-team risks

  • Unknown skill spread → Day 1–2 calibration exercise, tiering, and re-allocation on Day 3 (§5.2).
  • Silent blocking: an intern stuck for 3 h says nothing. Countered by the 90-minute blocker rule (§21).
  • Copy-paste architecture drift → template modules built first by D1 and used as the reference implementation.

Dependency risks

  • Everything depends on auth + RBAC + academic structure. These are front-loaded to Week 1–2 and owned by D1/D3.
  • Migrations conflict when 4 people add tables the same day — countered by the migration-window rule (§13.6).

Security / testing / deployment risks

  • Interns typically authorize in the UI only (hiding buttons). Policy tests for unauthorized access are mandatory per module.
  • Tests written last = tests never written. CI blocks merge without tests touching the changed namespace.
  • First deploy on release day = failure. Deployment rehearsal is Day 26 and Day 44 on staging.

7. Permission Matrix

Six roles in MVP. Principal, Department Head, Librarian, Receptionist and HR Manager are deliberately not created — the first two are satisfied by Institution Admin with a read-only permission set (create them as roles in Phase 2 when their distinct workflows exist), and the last three belong to excluded modules. 7.3 Rules that the matrix alone cannot express

  • PR-1 Teacher scope: a Teacher may act only on class_subjects where staff_id = auth()->user()->staff->id and the term is the current term. Enforced in AttendancePolicy, MarkPolicy, and a TeachesClassSubject gate — not in Blade.
  • PR-2 Student scope: every student-facing query is constrained by student_id = auth()->user()->student->id; direct-ID access to another student returns 403, never 404-with-details.
  • PR-3 Marks lock: once a result set is published, marks for that exam become read-only for everyone; corrections require an Admin/Registrar "unpublish" action which is audited and requires a typed reason.
  • PR-4 Attendance edit window: a teacher may edit a session for 48 hours; after that only Registrar/Admin, with a reason recorded.
  • PR-5 Separation of duties: the user who records a payment cannot delete it. Payments are never deleted — only reversed by a Super Admin with a reason, creating an offsetting record.
  • PR-6 Break-glass: exactly one Super Admin account exists at deploy; its password is rotated at handover and its every action is audited.
  • PR-7 A user may hold multiple roles (e.g. Registrar + Teacher); permissions are the union, but record-scope rules (PR-1/PR-2) still apply per role context.

10. Architecture

The architecture is deliberately plain Laravel. Every pattern below earns its place; anything not listed (repositories over Eloquent, DTOs everywhere, CQRS, hexagonal layering, a domain layer, modular packages) is banned for this project because it costs intern learning time and buys nothing at this scale.

13.3 GOOD vs BAD — the five areas interns get wrong

Validation & mass assignment

// BAD — no validation, mass assignment, no authorization
public function store(Request $request) {
    $student = Student::create($request->all());
    return redirect('/students');
}

// GOOD
public function store(StoreStudentRequest $request): RedirectResponse {
    $this->authorize('create', Student::class);
    $student = $this->students->admit($request->validated());   // service, transactional
    return to_route('people.students.show', $student)
        ->with('status', 'Student admitted. Admission number: '.$student->admission_no);
}

// StoreStudentRequest
public function authorize(): bool { return $this->user()->can('create', Student::class); }
public function rules(): array {
    return [
        'first_name'   => ['required','string','max:100'],
        'last_name'    => ['required','string','max:100'],
        'dob'          => ['required','date','before:today','after:1900-01-01'],
        'gender'       => ['required', Rule::enum(Gender::class)],
        'program_id'   => ['required', Rule::exists('programs','id')->where('is_active', true)],
        'email'        => ['required','email','max:255', Rule::unique('users','email')],
        'national_id'  => ['nullable','string','max:30', Rule::unique('students','national_id')],
        'guardians'                  => ['required','array','min:1'],
        'guardians.*.name'           => ['required','string','max:150'],
        'guardians.*.phone'          => ['required','string','max:20'],
        'guardians.*.relationship'   => ['required','string','max:50'],
    ];
}

Authorization

// BAD — UI-only authorization; the route is still reachable by URL
@if(auth()->user()->role === 'teacher')  <a href="/marks/{{ $cs->id }}">Enter marks</a>  @endif

// MarkPolicy.php
public function enter(User $user, ClassSubject $classSubject): bool {
    return $user->can('marks.create')
        && $user->staff?->id === $classSubject->staff_id
        && $classSubject->term->is_current

// Controller:  $this->authorize('enter', $classSubject);
// Blade:       @can('enter', $classSubject) ... @endcan
// Test:        asserts 403 for a teacher of a different class-subject

Queries / N+1

// BAD — N+1 and unbounded result set
$students = Student::all();
foreach ($students as $s) { echo $s->program->name; }

// GOOD — eager load exactly what the view needs, filter in SQL, paginate
$students = Student::query()
    ->with(['program:id,name', 'user:id,email'])
    ->when($request->search, fn ($q, $term) => $q->where(fn ($w) =>
        $w->where('admission_no', 'like', "{$term}%")
          ->orWhere('last_name', 'like', "%{$term}%")))
    ->when($request->program_id, fn ($q, $id) => $q->where('program_id', $id))
    ->when($request->status, fn ($q, $s) => $q->where('status', $s))
    ->orderBy('last_name')
    ->paginate(25)
    ->withQueryString();

Multi-step writes

// BAD — partial write leaves a paid invoice with no receipt
$payment = Payment::create($data);
$invoice->amount_paid += $data['amount'];
$invoice->save();
Mail::to($student)->send(new ReceiptMail($payment));   // failure here rolls back nothing

// GOOD — atomic, locked, event-driven side effects after commit
return DB::transaction(function () use ($invoice, $data, $user) {
    $invoice = Invoice::whereKey($invoice->id)->lockForUpdate()->firstOrFail();
    if (bccomp($data['amount'], $invoice->balance, 2) === 1) {
        throw new PaymentExceedsBalanceException();
    }
    $payment = $invoice->payments()->create([
        'receipt_no'  => ReceiptNumberGenerator::next(),
        'amount'      => $data['amount'],
        'method'      => $data['method'],
        'reference'   => $data['reference'] ?? null,
        'paid_at'     => $data['paid_at'],
        'received_by' => $user->id,
    ]);
    $invoice->amount_paid = bcadd($invoice->amount_paid, $data['amount'], 2);
    $invoice->balance     = bcsub($invoice->total, $invoice->amount_paid, 2);
    $invoice->status      = bccomp($invoice->balance, '0.00', 2) === 0
        ? InvoiceStatus::Paid : InvoiceStatus::PartiallyPaid;
    $invoice->save();
    PaymentRecorded::dispatch($payment);   // queued listener sends the email
    return $payment;
});

23.1 Definition of Ready (a task may not enter development without all six)

  1. The user story is written in role/action/value form and is understood by the person who will build it (they can restate it).
  2. Measurable acceptance criteria exist (§17 style — no "should work").
  3. Dependencies are identified and are either merged or covered by a written view-model contract.
  4. The design is sufficient: schema decided, wireframe or screen reference available, validation rules and authorization rules named.
  5. An owner and a reviewer are assigned.
  6. Test expectations are stated: which test cases will prove it, and which are automated vs manual.

D1 checks Readiness at the previous day's 16:45 slot. A task that is not Ready does not appear in tomorrow's stand-up; it goes back for refinement.

23.2 Definition of Done (a feature is Done only when all eleven hold)

  1. Implementation complete against the acceptance criteria — no stubs, no TODOs.
  2. Server-side validation complete on every input.
  3. Authorization complete: permission + policy + record scoping, with a 403 test.
  4. Database changes complete: migration, constraints, indexes, rollback verified.
  5. Tests complete: unit where logic exists, feature for every route, authorization tests for every role.
  6. Code reviewed and approved; all comments resolved.
  7. UI verified (DoD-U): responsive, empty state, error state, validation messages, confirmation on destructive actions.
  8. All acceptance criteria demonstrated to D1 — demonstrated, not claimed.
  9. Documentation updated in the same PR.
  10. No blocking defects (Critical or High) open against the feature.
  11. Merged into develop with CI green.

24.3 Rules

  • Reproduction is mandatory. A report without steps, expected result, actual result, role used, environment and a screenshot is returned to the reporter, not triaged. Bugs found in production also include the log reference ID shown on the error page.
  • Assignment: to the module owner by default. If the owner is unavailable or overloaded, the backup owner takes it. D1 never assigns more than 2 open bugs plus the day's feature task to one person (Rule 9).
  • Every fix carries a regression test that fails before the fix and passes after. No test, no merge — this is what stops the same bug returning in Week 7.
  • Verification is done by someone other than the fixer, on staging, using the original reproduction steps.
  • Bug budget: if open Critical + High exceeds 5 at any point, all feature work stops until it is back under 3. This rule is what prevents an unfixable Week 7.
  • After feature freeze (Day 40), only Critical and High fixes are merged. Medium/Low go to docs/known-issues.md and the Phase-2 backlog, visible to the PO.
  • Hotfix path (after Day 47): branch from main, minimal change, test, mentor approval, deploy, then merge back to develop the same day.

  9. Backup: run the backup command manually; confirm the artefact exists off-server.

27.6 Backup & restore

  • Nightly 02:00: full MySQL dump + storage/app archive, encrypted, copied off-server; 14-day retention; weekly copy retained for 3 months.
  • Failure of a backup run sends a notification to the admin email and appears on the dashboard.
  • Restore is tested, not assumed (Day 46): restore the most recent backup into a scratch database, run the smoke checklist against it, record the elapsed time. Documented in docs/guides/backup-restore.md with exact commands.

30. Complete Project SOP

School/University Management System — 49-Day Laravel Development SOP · v1.0 · Owner: Team Lead (D1) · Approver: Engineering Mentor · Review cadence: at each weekly checkpoint

30.1 Purpose

To define a single, binding way of working that allows six intern software engineers to deliver a secure, tested, deployable School/University Management System in 49 calendar days, and to make the state of that project visible and correctable every single day.

30.2 Scope

Applies to all engineering activity on this project from Day 1 to handover on Day 47: requirements, design, coding, review, testing, security, deployment, documentation, bug handling and communication. It applies to the MUST-HAVE MVP in §4.1. It does not authorize work on §4.3 POST-MVP items. Deviation requires written approval from D1 and the mentor.

30.3 Team

D1 Team Lead/Backend · D2 Backend (student domain) · D3 Backend (academic domain) · D4 Frontend/UI · D5 Full-stack (finance & communications) · D6 QA/Documentation/Release. An engineering mentor provides ≥1 h/day and holds approval authority over schema, security and release. Allocation is set on Day 3 from the calibration exercise and reviewed on Days 12 and 26.

30.4 Responsibilities

Per §6 and §22.1. Every module has exactly one owner and one backup owner. The backup owner reviews every PR for that module so no knowledge sits with one person. Nobody holds more than two active modules or more than two open bugs alongside a feature task.

30.5 Technology standards

Laravel 11 on PHP 8.3, MySQL 8.0, Blade + Tailwind + Alpine (no SPA framework, no Livewire), database queue and session drivers, Vite for assets. Approved packages are listed in §10.2 and no other package may be added without a written justification covering purpose, why Laravel-native is insufficient, optionality, and security/maintenance implications — approved by D1 and the mentor.

30.6 Development workflow

Requirement → Definition of Ready (§23.1) → design/contract → branch → implement with tests → self-check → PR before 16:00 → review in the 16:00 slot → address comments → merge to develop with green CI → QA verification → module sign-off at G4. Schema changes only in the 09:15–10:00 migration window. Everyone rebases at 10:00.

30.7 Git workflow

Per §14: main (release), develop (integration), short-lived feature/ and fix/ branches, hotfix/ from main only after release. Conventional commit prefixes. PRs capped at 400 lines, one approval minimum, two for schema/security/money. Tags at Days 19, 33, 40, 46 and 47.

30.8 Coding standards

Per §13: PSR-12 enforced by Pint, Larastan level 5, naming conventions, thin controllers, FormRequests for all validation, policies for all authorization, enums for all statuses, env() only in config, no $guarded = [], no $request->all(), no {!! !!} outside PDF templates, no DB::raw with user input. The GOOD/BAD examples in §13.3 are the reference the reviewer points to.

30.9 Database standards

Schema designed and mentor-reviewed before implementation (Rule 4), frozen on Day 5, extended only additively. Foreign keys restrict by default; cascade only on true child rows. Money is decimal(12,2) with bcmath arithmetic. Unique constraints on every business identifier. Indexes on every foreign key and every column used in a filter or sort. Soft deletes only where history matters, with the documented consequences for unique indexes. Every migration must roll back cleanly. Derived values are written only by services inside the same transaction as their source, and checked nightly by school:verify-integrity.

30.10 Security standards

Per §19. Security is built weekly, not reviewed at the end (Rule 5). Authorization is enforced by policy and middleware, never by hiding UI. Every state-changing route has a FormRequest. Uploads go to a private disk behind a policy-checked signed route. The route-audit test must stay green. The formal review is Day 43 and NFR-9 (zero open Critical/High) is a release gate.

30.11 Testing standards

Per §18. Tests ship in the same PR as the code (Rule 6); CI rejects controller/service changes without a matching test. Unit tests for all calculation logic, feature tests for every route, authorization tests for every role, two end-to-end workflow tests from Day 32. The manual regression pack is executed at Days 19, 33, 38, 43 and 46. Coverage target: services and policies ≥ 75% lines; 100% of MUST-HAVE acceptance criteria covered by a test.

30.12 Code review procedure

Reviewer assigned at task creation. Response within 4 working hours; the 16:00–16:45 slot is reserved so reviews never compete with coding. Review order: correctness → authorization → validation → tests → query efficiency → style. Style comments do not block alone. Every comment gets a reply; unresolved threads block merge. Schema, security and money PRs require D1 and the mentor.

30.13 Bug management

Per §24. Four severities with defined SLAs; reproduction steps are mandatory; every fix carries a regression test; verification by someone other than the fixer. Feature work stops when open Critical+High exceeds 5. After Day 40 only Critical/High are merged.

30.14 Daily management

Per §21. Stand-up 09:00 (15 min, three questions, no discussion). Migration window 09:15–10:00. Checkpoint at 11:30. Review slot 16:00. EOD report by 17:00 with evidence. The 90-minute blocker rule is mandatory, not discretionary. D1 updates the control board daily and checks: completed vs planned tasks, delayed tasks, blockers (internal and external), open bugs by severity, PRs awaiting review, tests pending, schema changes merged, staging/deployment status, and the week's risk status.

30.15 Weekly management

Checkpoints on Days 5, 12, 19, 26, 33 and 40. Each covers: functionality demonstrated live (not screenshots), quality status (bug counts, test counts, CI health), documentation status, risk review, scope review against §4, progress against the §5.3 hours plan, and next week's priorities. The PO attends and signs off on the modules demonstrated. Progress gates at Days 19, 26, 33 and 40 trigger §26 if missed by more than 10%.

30.16 Risk management

The §25 register is reviewed at every weekly checkpoint and whenever an early-warning signal fires. Each risk has an owner, a preventive mitigation already in the plan, and a contingency. New risks are added by anyone at stand-up. Risks that materialize become either a bug, a scope change, or an escalation — never a silent hope.

30.17 Change management

All change requests — from the client, the team, or a late answer to a §3.4 question — go to D1 in writing. D1 produces an impact assessment within one working day: effort, affected modules, risk, and which MUST-HAVE item of equal effort would be displaced. The PO chooses: accept with displacement, defer to Phase 2, or reject. Nothing is added "for free". After the Day-40 feature freeze, only Critical fixes are accepted; anything else goes to Phase 2. Every accepted change is recorded as an ADR and announced at stand-up.

30.18 Release management

Releases are tagged from main. v0.1.0 (Day 19), v0.2.0 (Day 33), v0.9.0-rc1 (Day 40, feature freeze), v1.0.0-rc2 (Day 46), v1.0.0 (Day 47). A release requires QA gate G5, the go/no-go decision, signed UAT, and the pre-deployment checklist. Release notes list features, fixed bugs, known issues and any migration requiring attention.

30.19 Deployment

Per §27. Two rehearsals (Days 26 and 44), the second executed by someone who did not write the runbook. Deployment is checklist-driven, verified by the post-deployment checklist, and reversible via the rehearsed rollback. Backups are configured before go-live and a restore is proven before release.

30.20 Handover

Per §29. Fifteen artefacts, each with an owner and an acceptance condition. Credentials are rotated at handover and team access is revoked and recorded.

30.21 Definition of Done

The eleven conditions in §23.2. A feature is Done or it is not Done; there is no "almost". "Done" claims require evidence: merged PR link, test names, screenshot, and the documentation file changed.

Appendix C — Data seeding & migration strategy

  • Factories for every model, with named states (e.g. Student::factory()->graduated()->withGuardian()). Tests build their own fixtures from factories and never depend on seeders.
  • ProductionSeeder (run on production): roles, the 78 permissions, default settings, the grade scale, and exactly one Super Admin whose password must be changed on first login and is rotated at handover. A test asserts it creates no operational data.
  • Reference seeders (optional in production, used in staging): AcademicStructureSeeder for a starter department/program/subject set the client can edit rather than type from scratch.
  • DemoDataSeeder (never production): deterministic with a fixed random seed — 240 students, 12 staff, full enrollment, 6 weeks of attendance, 2 exams with marks, published term-1 results, fee structures, invoices in mixed payment states, and one user per role with credentials listed in docs/guides/install.md.
  • PerfSeeder: scales to 5,000 students for NFR-1/2 measurement on Days 18, 39 and 44.
  • Clean-database guarantee: CI runs migrate:fresh --seed on every PR, so "it works on my machine because of leftover data" cannot happen.
  • Production data import: out of MVP scope (A8). If the client later provides legacy data, the procedure is: profile the source → map to the schema → build an importer command with a mandatory --dry-run producing a validation report → import into a staging copy → reconcile record counts and financial totals against the source → sign-off → import into production inside a maintenance window with a pre-import backup. This is a separate, separately-estimated engagement.
